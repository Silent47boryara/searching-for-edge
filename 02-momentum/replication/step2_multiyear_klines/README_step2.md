# Lab 06 — Этап 2: докачка многолетней истории 1d-klines

Скрипты написаны, **докачка не выполнялась**. Запускать локально самому.

## Что это делает

Качает дневные (1d) свечи по **всей вселенной USDT-M бессрочных фьючерсов
Binance**, за всю доступную в архиве историю, без привязки к датам сигналов
Klines. Это устраняет обе проблемы, из-за которых этап 1 (gate check) не смог
дать ответ: ступенчатое покрытие вселенной и смещённый состав монет.

Только klines. Ни OI, ни funding — они нужны на этапе 3 (издержки),
а не при первичном тесте на спред.

## Границы вселенной — сознательное решение, не упрощение

Вселенная: **только Binance USDT-M перпы (832 символа)**. Без капитализации,
без CMC, без других бирж и DEX. Причины зафиксированы в `PLAN.md`:

- momentum-эффект у LTW сильнее в неликвиде, которого на Binance perp
  физически нет;
- мультибиржевые данные добавляют survivorship bias уже на уровне самой
  биржи (какие площадки дожили и попали в выборку).

Отсюда следует, как читать будущий результат. **Это не повтор статьи один
в один и не её «грубая версия».** Это другой, самостоятельный вопрос:
работает ли momentum на реально торгуемой вселенной. Постановка честнее
и практически релевантнее, но и выводы переносятся не автоматически:

- **найдётся спред** → он найден там, где его можно исполнить;
- **не найдётся** → это не опровержение LTW: эффект может жить в сегменте
  мелких и неликвидных монет, который Binance перпами не листит.

Поля под капитализацию намеренно не добавляются — ни в докачку, ни в панель.
Size-фактор и value-weighted market-фактор из LTW на этих данных не строятся,
и попытки их подменить прокси в этой лаборатории не предпринимаются.

## Почему список символов берётся из S3, а не из `/fapi/v1/exchangeInfo`

`exchangeInfo` отдаёт только то, что торгуется **сейчас**. Монеты,
делистнутые в прошлом, из него исчезли — а это как раз те «умирающие»
активы, которые должны попадать в шорт-ногу momentum-стратегии. Без них
бэктест систематически льстит себе (survivorship bias).

S3-бакет `data.binance.vision` — архив, а не live-статус, делистнутые
символы в нём остаются. Замерено при написании скрипта:

| | |
|---|---|
| префиксов в архиве `futures/um/monthly/klines/` | 986 |
| из них поставочных/квартальных (`_250926`) — отсеиваются | 51 |
| бессрочных | 935 |
| **бессрочных с котировкой USDT — рабочая вселенная** | **832** |
| **есть в архиве, но нет в `exchangeInfo`** | **31** |

Эта 31 монета (`AERGOUSDT`, `ANCUSDT`, `ANTUSDT`, `BTCSTUSDT`, `BZRXUSDT`,
`BTTUSDT`, `AKROUSDT`, …) и есть то, что теряется при использовании
`exchangeInfo`. Скрипт сохраняет их список в `delisted_symbols.json` —
он понадобится для раздела про делистинг в `RESULT.md` этапа 3.

## Как запустить

```bash
cd step2_multiyear_klines  # (path relative to this replication/ folder)
```

Сначала посмотреть план без загрузки (только листинг, ~1–2 мин):

```bash
python3 download_multiyear_klines.py --dry-run
```

Основной запуск:

```bash
python3 download_multiyear_klines.py
```

В фоне, чтобы не держать терминал:

```bash
nohup python3 -u download_multiyear_klines.py > run_step2.log 2>&1 & echo "PID $!"
```

Следить за прогрессом:

```bash
tail -f download.log
```

После завершения — сборка панели (сеть не нужна):

```bash
python3 build_panel.py
```

Затем — проверка непрерывности покрытия (тоже без сети, несколько секунд):

```bash
python3 universe_timeline.py
```

Это прямая проверка, что докачка устранила ступенчатость этапа 1
(вселенная скакала по неделям 30 → 318 → 97 → 32 → 45 → 306 → 162).
Скрипт считает, сколько символов имеют цену закрытия в каждом календарном
месяце, и помечает флагом резкие изменения (|Δ| ≥ 20 символов И |Δ%| ≥ 25%).

Ожидается плавный рост — Binance листил перпы постепенно с конца 2019;
умеренные спады тоже норма, это делистинги. Тревожный признак — скачок
вверх и вниз подряд в середине истории: он означает, что покрытие снова
определяется наличием файлов, а не составом рынка. В этом случае проверить
`failures.csv` и перезапустить докачку, **а в отчёте этапа 2 скачки
зафиксировать, а не замолчать**.

### Полезные флаги

| флаг | смысл |
|------|-------|
| `--dry-run` | только листинг и оценка объёма, без загрузки |
| `--workers 20` | больше потоков (по умолчанию 12) |
| `--quote USDC` | другая котируемая валюта; `ALL` — все |
| `--interval 1h` | другой интервал (по умолчанию `1d`) |
| `--verbose` | подробный лог, видно каждый ретрай |

## Прерывание и продолжение

**Прерывать безопасно в любой момент.** Ctrl-C доканчивает текущие загрузки
и сохраняет состояние; повторный Ctrl-C выходит немедленно.

Checkpoint двухуровневый:

1. `manifest.json` — списки файлов по символам, полученные из листинга.
   При перезапуске 832 листинг-запроса не повторяются.
2. **Файлы на диске.** Перед загрузкой каждый файл проверяется на наличие
   и целостность zip; валидный пропускается (в логе — `skip`).

Файлы пишутся атомарно (`.part` → `rename`), архив проверяется **до** записи
на диск. Оборванная загрузка не оставляет битого файла, который потом
молча попал бы в панель.

Если что-то не скачалось — список в `failures.csv`, просто запустите скрипт
снова: он возьмёт только недостающее.

## Что на выходе

```
step2_multiyear_klines/
├── raw/<SYMBOL>/1d/<SYMBOL>-1d-YYYY-MM.zip   сырые архивы
├── manifest.json            checkpoint: какие файлы существуют
├── delisted_symbols.json    31 символ: в архиве есть, в exchangeInfo нет
├── failures.csv             что не скачалось (если было)
├── download.log             полный лог с прогрессом
├── после build_panel.py:
│   ├── panel_close.csv          дата × символ, закрытия
│   ├── panel_quote_volume.csv   дата × символ, оборот
│   └── panel_coverage.csv       по символу: диапазон, дни, пропуски, статус
└── после universe_timeline.py:
    └── universe_size_timeline.csv   месяц; активных символов; +диагностика
```

Колонки `universe_size_timeline.csv`:

| колонка | смысл |
|---------|-------|
| `month` | календарный месяц, `YYYY-MM` |
| `n_active` | символов с ценой закрытия хотя бы в один день месяца |
| `n_dense` | из них торговались ≥80% дней месяца |
| `n_new` / `n_gone` | появились / исчезли относительно прошлого месяца |
| `chg`, `chg_pct` | изменение `n_active` месяц к месяцу |
| `jump_flag` | 1 = резкое изменение, требует объяснения в отчёте |

`n_new` / `n_gone` отвечают на главный вопрос: реальный делистинг даёт
падение `n_active` с большим `n_gone`, а дыра в докачке — падение с
последующим возвратом тех же символов (`n_gone`, затем такой же `n_new`).

## Важно про сборку панели

`build_panel.py` **не заполняет пропуски** — ни forward-fill, ни
интерполяции. Отсутствие дня означает, что монета в тот день не торговалась.

Это принципиально: forward-fill превратил бы делистнутую монету в
«замороженную, но живую», и именно шорт-нога — та самая, ради которой
затевалась докачка — оказалась бы искажена.

`panel_quote_volume.csv` собирается сразу, хотя на этапе 2 не нужен: на
следующем шаге понадобится фильтр ликвидности, иначе momentum-корзина
наберётся из неторгуемого неликвида, который в реальности не исполнить.

Уточнение: `quote_volume` — **оборот, а не капитализация**. Это колонка,
которая и так лежит внутри уже скачанного файла klines, дополнительных
запросов и источников не требует. Используется только как фильтр
исполнимости, не как замена size-фактора. Если он не нужен — удалите
`quote_volume` из двух списков колонок в `build_panel.py`, на докачку
это никак не влияет.
